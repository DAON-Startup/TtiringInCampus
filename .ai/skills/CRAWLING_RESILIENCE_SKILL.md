# CRAWLING_RESILIENCE_SKILL.md — 크롤링 안정성 & 복구 스킬

## 목적
대학교 웹사이트 크롤링의 안정성을 보장하고, 장애 발생 시 자동 복구하는 표준 절차를 정의한다.

## 1. 크롤링 기본 규칙

### 예의 바른 크롤링 (Polite Crawling)
- `robots.txt`를 반드시 확인하고 준수한다
- 요청 간 최소 2초 딜레이를 유지한다 (rate limiting)
- User-Agent 헤더에 서비스명과 연락처를 명시한다
    - 예: `UnivNoticeBot/1.0 (+https://서비스도메인/bot-info)`
- 동시 요청 수를 소스당 최대 1개로 제한한다
- 학교 서버 부하가 적은 시간대(새벽 2~6시)에 전체 크롤링을 수행한다
- 실시간 모니터링용 크롤링은 1시간 간격으로 제한한다

### 법적 리스크 완화
- 크롤링 데이터는 공지사항 제목, 날짜, 카테고리, 본문 링크만 저장한다
- 본문 전문은 저장하지 않고, 사용자가 클릭하면 원본 페이지로 리다이렉트한다
- 단, AI 요약 리포트용으로는 본문을 임시로 메모리에 로드 후 요약만 저장한다
- 학교 측의 크롤링 중단 요청이 있으면 즉시 준수한다

## 2. 장애 감지

### 모니터링 지표
| 지표 | 정상 범위 | 경고 임계값 | 위험 임계값 |
|------|-----------|-------------|-------------|
| HTTP 응답 코드 | 200 | 4xx 연속 2회 | 5xx 연속 2회 |
| 응답 시간 | < 5초 | 5~15초 | > 15초 또는 타임아웃 |
| 크롤링 성공률 | > 95% | 80~95% | < 80% |
| 새 공지 감지 수 | > 0/일 (평일) | 0개/24시간 | 0개/48시간 (평일) |
| LLM 파싱 실패 | 정상 추출 | 부분 추출 (필드 누락) | 0건 추출 |

### 감지 방법
1. 매 크롤링 실행 후 응답 코드와 파싱 결과를 검증한다
2. 파싱된 공지 수가 0이면 HTML 구조 변경 가능성을 체크한다
3. 연속 3회 실패 시 해당 소스를 일시 중단하고 사람에게 알린다

## 3. 자동 복구 절차

### Level 1: 자동 재시도 (n8n Retry 노드)
```
n8n HTTP Request 실패 감지
  → n8n Retry 설정: 최대 3회, 간격 30초/60초/300초
  → 3회 실패 → Level 2 전환
```

### Level 2: 대체 전략 (n8n 워크플로우 내 처리)
- HTTP Request 노드에서 User-Agent 헤더 변경 (모바일 UA 등)
- 모바일 버전 URL로 전환하는 별도 분기 노드
- Google 캐시 버전 시도하는 별도 분기 노드

### Level 3: 사람 개입 요청
- Level 2까지 실패 시 n8n이 사람에게 알림 발송 (Slack/이메일/카카오톡)
- 알림 내용: 실패 소스, 실패 시각, 시도한 복구 방법, 추정 원인
- LLM 파싱이 실패한 경우 HTML 샘플을 함께 첨부

## 4. HTML 구조 변경 대응

**n8n + LLM 방식의 핵심 장점: CSS 셀렉터가 없으므로 구조 변경에 자동 대응**

LLM이 HTML을 직접 이해하므로 학교 웹사이트가 리뉴얼되어도:
1. **자동 대응**: LLM이 새로운 HTML 구조에서도 공지 목록을 추출할 수 있음
2. **감지**: LLM 파싱 결과가 0건이면 구조 변경 가능성 체크
3. **프롬프트 조정**: 파싱 실패 시 프롬프트를 더 구체적으로 수정하여 재시도
4. **에스컬레이션**: 프롬프트 조정 후에도 실패 시 사람에게 보고

> 기존 CSS 셀렉터 방식은 웹사이트 리뉴얼 시 반드시 코드 수정이 필요했지만,
> LLM 방식은 대부분의 구조 변경을 자동으로 흡수할 수 있다.

## 5. 데이터 중복 방지

- 각 공지사항의 고유 ID: `{소스코드}_{게시글번호}` 조합
- DB에 upsert 처리 (INSERT ON CONFLICT DO NOTHING)
- 공지 URL의 해시값을 보조 중복 검증에 사용
- 제목 + 날짜 조합으로 3차 중복 검증 (URL이 변경되는 경우 대비)

## 6. 크롤링 소스 설정 형식

각 크롤링 소스는 아래 JSON 형식으로 관리한다 (n8n 워크플로우 변수로 설정):

```json
{
  "source_id": "inu_cs_dept",
  "source_name": "인천대학교 컴퓨터공학부",
  "category": "학과",
  "base_url": "https://cse.inu.ac.kr",
  "list_url": "https://cse.inu.ac.kr/isis/3519/subview.do",
  "llm_parse_prompt": "아래 HTML에서 공지사항 목록을 추출하여 {external_id, title, posted_date, url} JSON 배열로 반환하라",
  "schedule": "0 */1 * * *",
  "max_pages": 3,
  "rate_limit_ms": 2000,
  "enabled": true,
  "n8n_workflow_id": "워크플로우 ID",
  "last_success": null,
  "consecutive_failures": 0
}
```

> **참고**: 기존 CSS 셀렉터(`selectors`) 필드 대신 `llm_parse_prompt` 필드를 사용한다.
> LLM이 HTML을 직접 이해하므로 소스별 셀렉터 유지보수가 불필요하다.
