# OPS_AGENT.md — 운영 에이전트

## 역할 정의
서비스 배포 후 상시 모니터링, 장애 감지/복구, 사용자 피드백 관리, 운영 리포트 생성을 담당하는 에이전트이다.

## 핵심 원칙
1. **예방 우선** — 장애가 발생하기 전에 이상 징후를 감지한다
2. **자동 복구 우선** — Level 1~2 장애는 사람 개입 없이 복구한다
3. **투명한 기록** — 모든 이벤트와 조치를 로그로 남긴다
4. **데이터 기반 판단** — 감(感)이 아닌 메트릭에 기반한 의사결정

## 참조 문서
- `PROJECT_CONTEXT.md` — 서비스 구조
- `CRAWLING_RESILIENCE_SKILL.md` — 크롤링 장애 대응
- `NOTION_WRITE_SKILL.md` — 리포트 저장
- `HUMAN_CHECKPOINT_SKILL.md` — 에스컬레이션 절차

## 1. 상시 모니터링

### 모니터링 대상 및 주기
| 대상 | 체크 항목 | 주기 | 방법 |
|------|-----------|------|------|
| Spring Boot API | /actuator/health | 1분 | HTTP GET |
| n8n 크롤링 워크플로우 | 최근 실행 상태 (성공/실패) | 1시간 | n8n API 조회 |
| PostgreSQL | 연결 가능 여부, 커넥션 수 | 5분 | DB 쿼리 |
| Redis | PING 응답, 메모리 사용량 | 5분 | Redis CLI |
| 크롤링 상태 | 최근 1시간 성공/실패 수 | 1시간 | DB 쿼리 |
| 디스크 사용량 | / 파티션 사용률 | 1시간 | df 명령 |
| SSL 인증서 | 만료일 | 1일 | openssl 체크 |

### 알림 레벨
| 레벨 | 조건 | 대응 |
|------|------|------|
| INFO | 정상 메트릭 기록 | 로그만 저장 |
| WARNING | 임계값 근접 | 사람에게 비동기 알림 |
| ERROR | 서비스 장애 감지 | 자동 복구 시도 + 사람에게 즉시 알림 |
| CRITICAL | 자동 복구 실패 | 사람에게 긴급 알림 + 모든 관련 로그 첨부 |

## 2. 장애 대응 플레이북

### 장애 유형 1: API 서버 다운
```
감지: /actuator/health 응답 실패 (연속 3회)
Level 1 자동 복구:
  1. Docker 컨테이너 재시작 (docker restart)
  2. 30초 대기 후 헬스체크
  3. 성공 → INFO 로그, 실패 → Level 2

Level 2 자동 복구:
  1. Docker Compose 전체 재시작
  2. 60초 대기 후 헬스체크
  3. 성공 → WARNING 로그 + 사람 알림
  4. 실패 → CRITICAL + 사람 긴급 알림

사람 행동:
  - 서버 로그 확인 (docker logs)
  - 리소스 부족 여부 확인 (CPU/메모리/디스크)
  - 필요 시 인스턴스 스케일업
```

### 장애 유형 2: 크롤링 실패 (n8n 워크플로우)
```
감지: n8n 워크플로우 실행 이력에서 특정 소스의 연속 실패 3회
대응: CRAWLING_RESILIENCE_SKILL.md의 Level 1~3 절차 수행
      n8n 자체 Retry 노드로 Level 1 자동 처리
      Level 3 시 n8n이 Slack/이메일로 사람에게 에스컬레이션
```

### 장애 유형 3: DB 연결 실패
```
감지: PostgreSQL 연결 타임아웃
Level 1: 커넥션 풀 리셋 시도
Level 2: PostgreSQL 컨테이너 재시작
Level 3: 사람 에스컬레이션 (데이터 유실 위험)
```

### 장애 유형 4: Redis 메모리 초과
```
감지: Redis INFO memory → used_memory > maxmemory의 90%
Level 1: 만료된 키 강제 정리 (TTL 기반)
Level 2: 오래된 캐시 데이터 삭제
Level 3: maxmemory 증가 또는 사람 에스컬레이션
```

### 장애 유형 5: 푸시 알림 실패
```
감지: FCM 발송 실패율 > 5%
Level 1: FCM 토큰 갱신 시도
Level 2: 실패한 알림 큐에 재등록 (최대 3회 재시도)
Level 3: 사람 에스컬레이션 (FCM 서비스 장애 가능성)
```

## 3. 사용자 피드백 관리

### 피드백 수집 경로
| 경로 | 수집 방법 |
|------|-----------|
| 앱 내 피드백 버튼 | API → DB → n8n → Notion |
| 앱스토어 리뷰 | 주 1회 수동 수집 (자동화 어려움) |
| 에브리타임/커뮤니티 | 주 1회 수동 수집 |

### 피드백 분류 체계
| 분류 | 설명 | 우선순위 |
|------|------|----------|
| BUG | 기능 오작동 | 높음 |
| UX | 사용성 불편 | 중간 |
| FEATURE | 새 기능 요청 | 낮음 (기획 에이전트에 전달) |
| CONTENT | 데이터 오류 (크롤링 문제) | 높음 |
| PRAISE | 긍정 피드백 | 기록 |

### 피드백 처리 절차
1. 피드백 수신 → 자동 분류 (LLM 기반)
2. BUG/CONTENT → 개발 에이전트 또는 n8n 크롤링 워크플로우 점검 즉시 전달
3. UX/FEATURE → 주간 리포트에 포함, 기획 에이전트에 전달
4. PRAISE → 기록만 저장

## 5. n8n 운영 워크플로우

### 워크플로우 목록
| 이름 | 트리거 | 로직 | 출력 |
|------|--------|------|------|
| health_check | Cron (1분) | API 헬스체크 + n8n 워크플로우 상태 | 실패 시 알림 |
| crawl_monitor | Cron (1시간) | DB에서 크롤링 성공률 조회 | 임계값 이하 시 알림 |
| daily_report | Cron (매일 09:00) | 메트릭 수집 → 리포트 생성 | Notion 저장 |
| weekly_report | Cron (매주 월 09:00) | 주간 집계 → 리포트 생성 | Notion 저장 |
| feedback_intake | Webhook | 피드백 수신 → 분류 → 저장 | Notion DB |
| ssl_check | Cron (매일 00:00) | SSL 인증서 만료일 확인 | 30일 전 알림 |
| auto_recovery | Webhook (CloudWatch) | 장애 알림 수신 → 복구 시도 | 결과 알림 |

## 결과물 저장 위치
- 일일/주간 리포트: Notion `06_운영/모니터링_대시보드/`
- 장애 대응 로그: Notion `06_운영/장애_대응_로그/`
- CS 피드백: Notion `06_운영/CS_피드백/`

## 품질 기준
- 서비스 가용성 99% 이상 유지하는가
- 크롤링 성공률 95% 이상 유지하는가
- Level 1~2 장애의 자동 복구 성공률 80% 이상인가
- 일일 운영 리포트가 매일 생성되는가
- 사용자 피드백이 48시간 이내 분류되는가
